# Phase 2: Research Feasibility Analysis

**Basis**: All classifications below are derived directly from the Phase 1 audit (`PHASE_1_CODEBASE_AUDIT.md`), including two empirical checks (patient-identity survival, selector gradient flow). No opinion or preference is expressed here — only what the current codebase can and cannot measure, and what a fix would cost.

## Project A — Adaptive Information-Driven MRI Slice Sampling

| Metric | Status | Evidence | Required modification | Difficulty |
|---|---|---|---|---|
| **Slice identity** (which of the 64 resampled indices was used) | **PARTIALLY** | `top_indices` computed (`final_model.py` line 367) but discarded on return (line 379 only returns `slice_scores`) | Change `AdaptiveSliceSelector.forward` return signature to include `top_indices`; thread through `encoder.forward` (currently discards `slice_scores` too, line 649-650) | **Low** — pure plumbing, no architecture change, ~10-20 lines |
| **Patient/case identity** | **PARTIALLY** | Confirmed empirically that `case`/`patient_id` survive the full MONAI transform + `DataLoader` collate pipeline unmodified; but `data_dicts` (line 234) only stores a combined `case` filename, not separated `patient_id`/`timepoint` fields | Add `patient_id`, `timepoint` keys at `data_dicts` construction time | **Low** — string parsing of existing path components already available at that point in the loop |
| **Slice loss** (per-slice segmentation loss, not just the fused central-slice loss) | **NO** | The decoder outputs one fused 2D prediction from the 9-slice-fused feature map; there is no per-slice prediction head, and supervision only exists for resampled-index 32 | Requires either (a) an auxiliary per-slice decoder head applied to each of the 9 `Conv2D5Stem` slice features before fusion, or (b) K forward passes with single-slice input and per-slice labels (both are available in `labels`, since the full 64-index label volume already exists, just currently only index-32 slice is extracted) | **Medium** — (b) is architecture-preserving (just more forward passes at eval time, no training change) but is not equivalent to "the loss the model was actually trained on"; (a) genuinely changes the model |
| **Slice uncertainty** | **PARTIALLY** | Evidential `alpha` (Beta distribution parameters) is computed but only for the *fused* 2D output, not per-input-slice | Same constraint as slice loss above — a per-slice uncertainty head does not currently exist | **Medium** — same options/cost as slice loss |
| **Slice confidence** | **PARTIALLY** | The `Conv2D5Stem` per-slice softmax attention weight (`alphas`, lines 450-452) is a genuine, already-differentiable, already-trained proxy for "how much this slice mattered to the fusion" — but it is not confidence in the statistical/calibration sense, just a learned fusion weight | Capture and log the existing `alphas` tensor (currently computed then only used inline, never returned or logged) | **Low** — additive return-value change, reuses an existing computation |
| **Slice difficulty** (how hard is this slice to segment) | **NO** | No mechanism computes a per-slice difficulty score at all; difficulty would need to be defined (e.g., per-slice Dice under (b) above, or lesion-boundary density as a data-derived proxy) and then computed | New code required in both dataset-prep and metric-computation | **Medium-High** — requires a definition decision plus new computation, not just logging |
| **Slice redundancy** (do selected slices carry overlapping information) | **NO** | No correlation/overlap computation exists anywhere in the codebase | Entirely new: e.g., pairwise feature-similarity or mutual-information estimate between the 9 selected slices' `Conv2D5Stem` outputs before fusion | **High** — new metric definition, new computation, no existing scaffold to build on |
| **Slice evolution over epochs** (does the selection change as training progresses) | **PARTIALLY** | Depends entirely on slice-identity logging (item 1) existing first; if `top_indices` is logged per epoch, evolution is just a groupby-over-epoch on that log | Same fix as slice identity, plus persisting per-epoch instead of per-batch-only in memory | **Low**, but strictly gated on fixing item 1 first |

### Critical precondition finding (not a metric, a foundational risk)

Per Phase 1 §6, **the `AdaptiveSliceSelector`'s scorer network receives zero gradient from the task loss**, confirmed empirically (`torch.topk` blocks the gradient path; `selected_volume` is gathered from the raw input, not the scorer's own features). This is upstream of every metric in the table above: it is possible to *measure* slice scores, confidence, and identity even if the mechanism is not learning — but any research question of the form *"does adaptive selection improve as training progresses"* or *"does the model learn to prefer informative slices"* is currently **not testable**, because the mechanism does not learn under the current implementation, regardless of how much instrumentation is added.

**What would be required to make this testable** (this is a scope decision the research direction must make explicitly, not something instrumentation alone resolves):
- **Option 1 — Soft/differentiable selection**: replace hard `topk` with a soft-attention weighting over all 64 slices (Gumbel-softmax top-k, or a learned soft mask applied multiplicatively before the stem). Architecture change, not instrumentation. Difficulty: **Medium** (well-established technique, e.g., differentiable top-k literature) but is squarely "implementing the research idea," not diagnostics.
- **Option 2 — Straight-through estimator**: keep hard selection in the forward pass but pass a surrogate gradient (e.g., softmax over scores) backward. Difficulty: **Medium**, smaller code diff than Option 1, but changes training dynamics.
- **Option 3 — Treat current selector as a fixed/random baseline and study fixed-vs-random-vs-heuristic slice selection instead**, sidestepping the "does it learn" question entirely and reframing the research question around comparing *selection policies* rather than *learning a selection policy end-to-end*. Difficulty: **Low** (no code change needed beyond swapping which indices get used), but this is a materially different (narrower) research claim than "adaptive, information-driven" implies.

**This finding should be treated as load-bearing for any Project A go/no-go decision** — it is not an instrumentation gap, it is a mechanism gap.

## Project B — Optimization of Multi-Objective Loss Functions for Uncertainty-Aware Segmentation

| Metric | Status | Evidence | Required modification | Difficulty |
|---|---|---|---|---|
| **Individual losses** (Dice, FocalTversky, Evidential, separately) | **PARTIALLY** | All three are computed as distinct Python objects/values before being summed into `loss` (lines 1381-1387), but only the *combined* value is logged to `train_logs.csv` (`loss`, `dice`, `mean_evidence` — no `loss_dice`/`loss_ft`/`loss_evid` breakdown) | Extract and log each component separately before summation — prototyped in this session's `loss_logger.py` | **Low** — pure logging addition, zero training-behavior change |
| **Gradient norms** (total, per-parameter-group, per-layer) | **NO** | Confirmed by full-file read: no `.grad`, `torch.norm(...grad...)`, or gradient-inspection code exists anywhere in `final_model.py` outside what was added in this session's diagnostic modules | Insert norm computation between `.backward()` and `.step()`; under AMP (`GradScaler`), must call `scaler.unscale_(optimizer)` before measuring, or logged norms will be scaled by the AMP loss-scale factor and not physically meaningful | **Low-Medium** — the AMP unscale step is a real correctness detail, not just "add a print" |
| **Gradient flow** (which components — encoder/decoder/CBAM — receive how much gradient) | **NO** | Same as above; however the two-optimizer-group structure (`encoder_params` vs `decoder_params`, lines 1749-1750) already gives a natural, pre-existing split to report against | Group-wise norm computation using the existing `optimizer.param_groups` structure | **Low** — the grouping already exists in the optimizer config, just needs to be read out |
| **Gradient cosine similarity** (do Dice/FocalTversky/Evidential push parameters in the same direction) | **NO** | No such computation exists | Requires computing each loss's gradient *separately* (i.e., three extra `.backward(retain_graph=True)` calls per batch, since by default only the summed `loss_total` is backpropagated once) — this is fundamentally more expensive than the other metrics because it triples the backward-pass cost | **Medium** — correct implementation is straightforward (prototyped in this session's `gradient_similarity.py`) but the *performance cost* (~20-30% slower per batch if run every batch) is a real constraint, not just an implementation detail |
| **Parameter updates** (actual Δθ per step, not just gradient magnitude) | **NO** | Not computed; would differ from gradient norm because AdamW applies per-parameter adaptive scaling + weight decay, so gradient norm alone does not equal update magnitude | Snapshot `param.data` before/after `optimizer.step()` and diff (cheap), or reconstruct from AdamW's internal `exp_avg`/`exp_avg_sq` state (more informative but requires reading optimizer internals) | **Low** (before/after diff) to **Medium** (reading Adam moment estimates) |
| **Layer-wise gradients** | **NO** | Same absence as above; `model.named_parameters()` already gives clean per-layer names for free (confirmed structurally: encoder stages, CBAM, decoder up-blocks all have distinct, greppable names) | Iterate `named_parameters()` after backward, log per-name norm | **Low** — prototyped in this session's `gradient_logger.py` |

### Notes specific to Project B's feasibility

- **No mechanism gap exists for Project B**, unlike Project A. Every metric in the table is a **pure instrumentation gap** — the underlying training mechanism (multiple losses summed into one scalar, standard AdamW, standard AMP) is exactly the kind of system this class of diagnostic is designed for. There is no equivalent to Project A's "the mechanism doesn't learn" problem.
- **The two disabled loss components** (consistency, pseudo-label) are architecturally present but contribute nothing under default config. If the research question for Project B is scoped to *"how do Dice, FocalTversky, and Evidential interact"* (the three currently-active losses), instrumentation alone suffices. If the research question is scoped to *"how would consistency/pseudo-label losses interact with the rest if enabled,"* that requires flipping `USALD_CONSISTENCY_ENABLED`/`USALD_FDR_ENABLED` to `True`, which is a **training-behavior change**, not instrumentation, and would need to be scoped explicitly as part of committing to that version of the research question.
- **AMP interacts with every gradient-based measurement.** `GradScaler` scales the loss before `.backward()` specifically to prevent fp16 underflow; raw `.grad` values immediately after `.backward()` (and before `scaler.step()`) are scaled by an internal factor (`scaler.get_scale()`, dynamically adjusted) and are not directly comparable across batches unless either (a) `scaler.unscale_()` is called first, or (b) the scale factor is logged alongside and divided out post-hoc. This is a small but real correctness requirement that must be part of Phase 3's implementation, not an afterthought.

## Side-by-Side Feasibility Summary

| | Project A | Project B |
|---|---|---|
| Metrics fully measurable today (YES) | 0 / 8 | 0 / 6 |
| Metrics partially measurable (PARTIALLY) | 4 / 8 (identity, patient ID, confidence-proxy, evolution — all gated on low-cost logging fixes) | 1 / 6 (individual losses — gated on low-cost logging fix) |
| Metrics requiring new computation (NO) | 4 / 8 (slice loss, uncertainty, difficulty, redundancy — all require either new forward passes or new architecture) | 5 / 6 (all gradient-related metrics — all require new instrumentation, none require architecture change) |
| Does a foundational **mechanism gap** exist (not just a measurement gap)? | **Yes** — the selector is empirically confirmed non-trainable via backprop under the current implementation | **No** — the loss/gradient system works as a standard multi-term objective; every gap is measurement-only |
| Cheapest fixes | Low-difficulty: slice identity, patient ID, confidence-proxy (all plumbing) | Low-difficulty: individual loss logging, gradient norms, layer-wise norms (all plumbing) |
| Most expensive fixes | High-difficulty: slice redundancy (new metric, no scaffold); mechanism fix for trainability (architecture change, arguably out-of-scope for "instrumentation") | Medium-difficulty: gradient cosine similarity (correct but expensive — up to 4x backward passes per measured batch) |
